# ADR: формат артефактов Kubernetes

Статус: принято. Закрывает требование задачи #59 «принято и обосновано решение
о формате артефактов Kubernetes».

## Контекст

Docker Compose остаётся способом локального запуска и односерверной установки.
Промышленная эксплуатация (до 400 одновременных пользователей) требует
Kubernetes-топологии с независимым масштабированием LiteLLM, Presidio Analyzer,
Triton и `codex-lb`.

Особенности проекта, определяющие выбор формата:

- Все компоненты релизятся **единым согласованным комплектом**: смешанный запуск
  разных версий LiteLLM и Analyzer с общим Redis не поддерживается
  ([architecture.md](architecture.md), раздел «Числа в JSON»).
- Миграции обеих PostgreSQL должны выполняться **единственным управляемым
  заданием до запуска новой версии** приложений (#59).
- Требуются воспроизводимая установка на нескольких окружениях
  (integration/production) и документированный откат.
- `codex-lb` разворачивается **официальным Helm chart** (#59), формат решения
  должен позволять подключать его как зависимость.

## Рассмотренные варианты

### Helm umbrella chart — выбран

**Плюсы**

- Единый версионируемый артефакт на весь стек: версия чарта = версия релиза,
  публикация в OCI-реестр, закрепление по версии/digest.
- Helm hooks (pre-install/pre-upgrade Job) — штатный механизм миграций БД
  до rollout приложений.
- Встроенные `helm rollback`, `helm upgrade --wait`, history — основа
  процедур обновления и отката.
- Значения по окружениям (`values.<env>.yaml`) без дублирования шаблонов.
- Официальный chart `codex-lb` подключается декларативно через `dependencies`.
- Шаблоны probes, PDB, NetworkPolicy, HPA — в одном месте, проверяются
  `helm lint`/`helm template` в CI.

**Минусы**

- Go-шаблоны сложнее чистого YAML; ошибки values всплывают на
  `helm template`/upgrade, а не при написании.
- Единый жизненный цикл: обновление одного компонента вне релиза стека —
  только через `--set <comp>.image.tag`.

### Helmfile

**Плюсы**: независимые релизы на компонент, свой набор values на окружение.
**Минусы**: два слоя инструментов (helm + helmfile); порядок установки и
миграции описываются вручную; нет единого артефакта релиза. Для проекта, где
версии компонентов жёстко связаны, независимость релизов — источник риска
рассинхрона, а не преимущество.

### Kustomize

**Плюсы**: чистый YAML без шаблонов, декларативные overlay, kubectl-native.
**Минусы**: нет hooks (миграции выносятся в CI), нет rollback, нет
пакетирования/версионирования; зависимость от внешнего чарта `codex-lb`
не выражается.

### Минимальные эталонные манифесты

**Плюсы**: максимальная прозрачность, нулевая tooling-зависимость.
**Минусы**: не масштабируется на 2+ окружения и 5 компонентов без самописной
генерации; миграции, откат, версии — вручную; высокая цена сопровождения.

## Решение

**Helm umbrella chart** `deploy/helm/ru-llm-proxy` с локальными subchart'ами
(`litellm`, `litellm-jobs`, `presidio-analyzer`, `ner-triton`) и зависимостью
на официальный chart `codex-lb` (`oci://ghcr.io/soju06/charts/codex-lb`).

Обоснование: Helm штатно закрывает три ключевых требования — единый
согласованный релиз, миграции БД до запуска новой версии, документированный
откат — без дополнительных слоёв инструментов. Цена (сложность шаблонов)
сдерживается малым набором флагов и двумя фиксированными values-файлами
(integration/production).

Привязка к конкретному ingress-контроллеру не выполняется: Istio-шаблоны
находятся за флагом `istio.enabled`, предусмотрен fallback на стандартный
Ingress (требование #59 «вне задачи» о vendor-lock).

## Последствия

- Обновление стека = `helm upgrade` новой версией чарта; откат = `helm rollback`
  (плюс процедура восстановления БД при несовместимых миграциях).
- Миграции LiteLLM: pre-upgrade Job (`DISABLE_SCHEMA_UPDATE=false` в Job,
  `true` в Pod'ах). Миграции codex-lb: штатный механизм официального чарта.
- Секреты — только `existingSecret`/External Secrets Operator; в values
  секретных значений нет.
- Образы закрепляются по тегу/digest в values; `latest` запрещён.
